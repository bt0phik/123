# FarSight LOD — экспериментальный Fabric-мод для Minecraft Java 26.3

## Новый этап
- Рендеринг переведён на современную схему Fabric `LevelRenderEvents` и Minecraft render pass API.
- CPU-меши из кэша передаются в `StagedVertexBuffer`, затем рисуются отдельным проходом.
- Радиус отсечения учитывает обычную дальность Minecraft и выбранный LOD-радиус.
- Сборщик данных по-прежнему читает только уже загруженные чанки; принудительной загрузки нет.

## Статус и ограничения
Это экспериментальный прототип, **не готовый релиз**. Я не могу собрать его здесь, потому что Gradle в среде не установлен, и не могу запустить Minecraft для проверки. API 26.3 активно меняется; возможны несовпадения имён/сигнатур с точными mappings. Даже после исправления компиляции дальние чанки из не загруженных областей пока не появятся — для этого нужна отдельная система извлечения/сохранения terrain data и её обновления по мере исследования мира.

## Сборка
Нужны JDK 25, Gradle 9.6.0, Fabric Loader 0.19.5+, Fabric API для Minecraft 26.3 и Mod Menu.
```sh
gradle build
```


## Сохранение LOD-данных (экспериментально)

Отсканированные поверхностные тайлы сохраняются в `farsight-lod/` внутри папки игры, отдельно для идентификатора сервера/мира и измерения. При входе загружаются до 2048 ближайших тайлов, чтобы ограничить первоначальную нагрузку. Кэш содержит только высоту поверхности и цвет, а не полный блоковый чанк. Мод по-прежнему не принудительно загружает чанки.

Важно: это всё ещё прототип. Персистентный кэш позволяет повторно использовать уже снятые образцы, но сам по себе не создаёт карту неисследованной местности и не заменяет полноценный многомасштабный LOD-пайплайн.

## Этап 3 — обновление поверхности и ограничение памяти
- Кэш периодически переснимает уже загруженные чанки, чтобы изменения поверхности со временем попадали в дальний ландшафт.
- Если высоты и цвета не изменились, меш не перестраивается и файл не перезаписывается.
- Периодическая очистка оставляет в оперативной памяти до 8192 ближайших тайлов; файлы на диске не удаляются.
- Это снижает бесконтрольный рост CPU-кэша при долгих путешествиях. Пересъёмка выполняется постепенно, не принудительно загружает чанки.

Ограничение: повторное сканирование использует грубую сетку 5×5 и проверяет только чанки, уже загруженные ванильной игрой. Это не полноценная поддержка изменения каждого блока и не генерация данных неисследованных территорий.


## Этап 4: границы чанков и лишняя работа рендера

- Сетка LOD теперь берёт граничные точки на координатах 0, 4, 8, 12 и 16. Если соседний чанк уже загружен, его поверхность используется для общей границы; если нет — край дублируется без принудительной загрузки чанка. При последующем обновлении соседние тайлы могут выровняться.
- Проверка дальности в рендерере использует квадрат расстояния и не вычисляет квадратный корень для каждого тайла каждый кадр.
- Пустые меши пропускаются.
- Полная сборка Minecraft 26.3 всё ещё требует проверки в среде с JDK 25 и Gradle; рендер API версии 26.3 остаётся экспериментальным.


## Этап 5: устойчивость файлов

- Настройки сохраняются через временный файл и атомарную замену, чтобы внезапное закрытие игры с меньшей вероятностью повредило JSON-конфиг.
- Загрузчик тайлов отклоняет записи с лишними байтами; повреждённый файл не должен мешать загрузке остальных тайлов.
- Это повышает устойчивость сохранения, но не заменяет полноценную сборку и игровой тест на Minecraft 26.3.


## Этап 6: согласование с рендер API Minecraft 26.3

- Обновлены импорты графического API под RenderPearl, используемый Minecraft 26.3: pipeline, topology, vertex format, render pass, GPU buffer slice и texture view.
- Идентификатор pipeline переведён на `Identifier`, а цветовой буфер очищается через `OptionalInt.empty()`, как в актуальной сигнатуре render-pass API.
- Pipeline передаётся в render pass через `RenderSystem.getCompiledPipeline(...)`.
- Это исправления по опубликованным API-описаниям 26.3, но без JDK 25, Gradle и запуска игры компиляцию всё ещё нельзя честно подтвердить.

- Дополнительно: рендерер теперь не создаёт GPU draw и не запускает upload, если в кадре нет ни одного подходящего тайла; проверка видимости переиспользуется в обоих проходах. Для поверхности отключено отсечение обратных граней, чтобы рельеф не исчезал из-за направления треугольников.

## Этап 7: совместимость меню и сокращение работы кадра

- Экран настроек переведён с Yarn-имён классов на официальные имена Mojang, которые использует текущая конфигурация Loom для Minecraft 26.3 (`Screen`, `Button`, `Component`, `GuiGraphicsExtractor`). Это устраняет очевидную причину ошибок компиляции в Mod Menu.
- Рендерер теперь формирует список видимых мешей за один проход по кэшу, а не проверяет все меши повторно перед отрисовкой.
- Проверка сборки в этой среде всё ещё невозможна: доступна Java 21, нет установленного Gradle и нет сетевого доступа для загрузки JDK 25/зависимостей. Поэтому этот этап — исправление исходников, а не подтверждённый рабочий JAR.

## Сборка на Windows

1. Установи JDK 25 и Gradle 9.6.0.
2. Открой `cmd` в папке проекта (там, где лежит `build.gradle`).
3. Выполни `gradle build`.
4. Если сборка прошла, JAR будет в `build/libs/`. Скопируй его в `mods` профиля Minecraft 26.3 вместе с Fabric API. Mod Menu нужен только для экрана настроек.

Сначала проверяй мод в отдельном тестовом мире и сохрани резервную копию важного мира.

## Этап 8: порядок отрисовки

- Перенёс LOD-поверхность на событие `BEFORE_TRANSLUCENT_TERRAIN`: она должна отрисовываться после непрозрачного ландшафта и сущностей, но до воды и других прозрачных поверхностей. Это правильнее для непрозрачной дальнобойной поверхности, чем прежний проход после прозрачного рельефа.
- Нужен игровой тест: фактический порядок кадров и поведение глубины должны быть подтверждены запуском Minecraft 26.3.


Примечание buildfix4: зависимость Mod Menu временно убрана из сборки, чтобы сборка не зависела от доступности сервера maven.terraformersmc.com. Экран настроек через Mod Menu пока не подключён.
